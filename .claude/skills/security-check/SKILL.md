# Streamlit + LLM アプリ セキュリティチェック

## このスキルの目的

Streamlit で作った LLM 連携アプリ（個人用ツールから社内デモまで）には、繰り返し現れる典型的な穴がある。
APIキーがコードやログに漏れる、ユーザー入力をそのままプロンプトへ流し込む、モデル出力を生HTMLとして描画してXSSになる、
依存パッケージを固定せず既知の脆弱性を抱える――こうした問題は「攻撃を受けてから」では遅い。

このスキルは、人間のセキュリティレビュアーが行う作業を体系化したものだ。
コードを網羅的に読み、4つの観点で穴を探し、**重大度順に並べた所見レポートと具体的な修正提案**を出す。
勝手にコードを書き換えるのではなく、まず人が判断できる材料を出すのがゴール（修正はレポートで提案する）。

なぜレポート＋提案なのか：セキュリティの修正は「文脈次第で正解が変わる」ことが多い。
個人用ローカルツールと公開アプリでは、同じ所見でも対応の優先度がまるで違う。
だから機械的に直すのではなく、リスクと根拠を説明したうえで判断を委ねる。

## 進め方

### 1. 対象とコンテキストを掴む

まず「これは誰が・どこで使うアプリか」を把握する。リスク評価の前提になる。

- エントリーポイント（`Home.py` / `app.py` / `streamlit_app.py` 等）と `pages/` 配下を一覧する
- LLM呼び出しを集約しているモジュール（`utils/`、`*_client.py`、`api.py` 等）を特定する
- `requirements.txt` / `pyproject.toml`、`.env*`、`.gitignore`、`.streamlit/` を確認する
- このアプリが「ローカル個人利用」なのか「ネット公開／共有」なのかを推定し、レポート冒頭に明記する（後述のリスク文脈）

### 2. 機械的スキャンを先に走らせる

`scripts/scan.py` を実行すると、検出しやすい項目（ハードコードされたキーらしき文字列、`.env` が `.gitignore` に入っているか、
`unsafe_allow_html=True` の使用箇所、`requirements` のバージョン非固定、`eval`/`exec`/`subprocess` の使用）を一括で洗い出せる。
毎回手でgrepし直す無駄を省くための出発点だ。

```bash
python .claude/skills/security-check/scripts/scan.py <対象ディレクトリ>
```

スキャナは「当たりをつける」ためのもの。出力を鵜呑みにせず、各ヒットを実際にコードで確認し、
逆にスキャナが拾えない設計レベルの問題（プロンプト構造、出力の使われ方）は次のステップで人の目で追う。

### 3. 4観点で精査する

各観点の詳細なチェック項目・典型パターン・誤検知の見分け方は `references/checklist.md` にまとめてある。
**精査に入る前に必ず一度読むこと。** ここでは要点だけ示す。

1. **シークレット漏洩** — APIキー等の機密が、コード・設定・ログ・エラー画面・git履歴に露出していないか。
   `st.error(f"...: {e}")` のような例外そのままの表示や、`st.write(os.environ)` 系の取り違えにも注意。

2. **プロンプトインジェクション** — ユーザー入力が f-string などでプロンプトやシステム指示に直結していないか。
   入力で指示を上書きできる構造になっていないか。モデル出力を後続処理（ツール実行・ファイル書き込み・SQL）に
   無検証で渡していないか。入力長の制限はあるか。

3. **出力・XSS・unsafe_html** — モデル出力やユーザー入力を `st.markdown(..., unsafe_allow_html=True)` や
   `st.components.v1.html(...)` で生HTMLとして描画していないか。`st.markdown` のデフォルト（HTMLエスケープあり）は安全側だが、
   `unsafe_allow_html=True` を付けた瞬間にXSS面が開く。出力をファイルパスやコマンドに流用していないか。

4. **依存関係の脆弱性** — `requirements.txt` 等でバージョンが固定されているか、既知CVEを抱えるパッケージがないか。
   可能なら `pip-audit` を試す（未導入なら導入は提案にとどめ、無理に実行しない）。

### 4. リスク文脈を踏まえて重大度を付ける

同じ所見でも、公開アプリと手元ツールでは重大度が変わる。ステップ1で掴んだ前提に照らして判定する。
過剰に煽らない・過小にもしない。たとえば「個人用ローカルツールで、入力者＝APIキー所有者本人」なら、
プロンプトインジェクションの実リスクは低い――その事実をレポートに正直に書く。それが信頼できるレビューだ。

## レポートの出力フォーマット

必ず次の構成で出力する（Markdown）。最後に画面表示し、ユーザーが希望すれば `SECURITY_REVIEW.md` に保存する。

```markdown
# セキュリティレビュー結果

## 前提（リスク文脈）
- 対象: <アプリ名 / 構成（Streamlit + 使用LLM）>
- 想定利用形態: <ローカル個人利用 / 公開・共有 / 不明（推定根拠も）>
- この前提が重大度判定にどう影響するかを1〜2行で

## サマリー
| 重大度 | 件数 |
|--------|------|
| Critical | n |
| High | n |
| Medium | n |
| Low | n |
| Info | n |

最優先で対応すべき項目を2〜3行で要約。

## 所見

### [重大度] 所見タイトル
- **場所**: `path/to/file.py:行番号`
- **観点**: シークレット漏洩 / プロンプトインジェクション / 出力・XSS / 依存関係
- **内容**: 何が問題か（該当コードを短く引用）
- **なぜ問題か**: 攻撃シナリオ・影響を具体的に
- **修正提案**: 具体的なコード or diff。複数の選択肢があるなら併記し、この文脈での推奨を示す

（所見ごとに繰り返し。重大度の高い順に並べる）

## 良い点
セキュアに作られている箇所も挙げる（例: st.markdown が unsafe_allow_html 未指定、.env が gitignore 済み）。
レビューの公平性を示し、すでに正しい部分を壊させないため。
```

重大度の目安：
- **Critical** — 機密が実際に露出している（コミット済みのキー、公開時に誰でも到達できる漏洩経路）
- **High** — 公開・共有された瞬間に悪用可能（XSS、無検証のツール実行への出力受け渡し）
- **Medium** — 条件次第で問題になる、防御が不足している
- **Low** — 設計上の改善が望ましいが直接の実害は限定的
- **Info** — 注意喚起・ベストプラクティス

## 原則

- **再現コードや攻撃の完成形は書かない。** 防御に必要な範囲で「どう悪用されうるか」を説明するにとどめる。
- **誤検知を恐れず、しかし正直に。** 確信が持てない所見は「要確認」と明示する。断定できないことを断定しない。
- **既存の良い実装を壊さない。** 修正提案は最小限で、アプリの動作・日本語UIの方針を尊重する。
